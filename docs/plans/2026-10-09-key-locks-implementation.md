### Глоссарий

| Термин | Значение |
|---|---|
| Сейф | Полка, закрытая с начала попытки и заполненная предметами. Открывается своим ключом, после этого навсегда становится обычной |
| Ключ | Особый элемент очереди колонки. Не предмет: не имеет `ItemType`, не участвует в матче и подсчёте групп |
| Предметов перед ключом | Сколько предметов колонки стоит между передним краем и ключом. Ноль — ключ впереди |
| Сбор ключа | Автоматическое снятие ключа, который оказался впереди, и открытие его сейфа |
| Знак замка | Пара «цвет + форма» (●, ▲, ■), общая для ключа и его сейфа. Выводится из порядка сейфов в определении уровня, в данных не хранится |
| Запрос на изменение доски | Элемент очереди `GameSession.RequestBoardChange`, уже используется конвейерами |

## 2. Правила механики (норматив)

| № | Правило |
|---|---|
| K1 | Сейф содержит обычные очереди с начала попытки. Открытие не создаёт и не уничтожает предметы |
| K2 | С сейфа нельзя брать предметы, на него нельзя переносить и с ним нельзя меняться. Ряд за решёткой не собирается |
| K3 | Ключ — элемент очереди колонки открытой обычной полки. На старте перед ключом минимум один предмет |
| K4 | Ключ впереди собирается автоматически. Пока он не собран, у колонки нет переднего предмета: её нельзя взять, на неё нельзя положить, она не участвует в матче |
| K5 | Сбор ключа удаляет его из колонки и открывает его сейф навсегда. Следующий предмет колонки становится передним |
| K6 | Сбор не считается ходом: не даёт очков, комбо, времени и не двигает другие механики |
| K7 | Матчи, возникшие после открытия, разыгрываются обычными каскадами с очками и комбо |
| K8 | Если в одном действии впереди оказались несколько ключей, каждый собирается ровно один раз. Порядок сбора — по индексу полки с ключом, затем по индексу колонки |
| K9 | Победа — когда на доске нет предметов и нет незавершённых изменений. Сейфы к этому моменту обязательно открыты: в каждом есть предметы |
| K10 | Пауза останавливает перелёт ключа и открытие дверцы. Перезапуск отменяет ожидающие сборы |
| K11 | Действие, принятое до конца времени, и вызванные им сборы доигрываются. Результат объявляется после этого, как сейчас у конвейеров |
| K12 | Подсказка учитывает открытие сейфа и не предлагает ход, пока сбор ожидает выполнения или выполняется |

Следствие K3–K5. Вставка ключа в колонку не меняет ход игры по предметам. Ключ собирается в тот же момент, когда открылся бы предмет за ним, и все матчи и каскады остаются прежними. Ключ меняет только одно: когда открывается сейф. На этом построен генератор (раздел 5.8).

## 4. Зафиксированные решения

| Тема | Решение | Почему |
|---|---|---|
| Как хранить ключ | Отдельный список ключей колонки: «предметов перед ключом» + индекс сейфа. Список предметов не меняется | Код, который считает типы, группы, глубину и матчи, продолжает работать с `Items` без правок. Новый `ItemType.Key` пришлось бы исключать вручную везде (концепт, раздел 6) |
| Ссылка на сейф | Физический индекс полки | Простой и однозначный вариант. Поэтому полки досок с ключами не переставляются при нормализации ключа поиска |
| Сейф в данных | `_isClosed` раскладки полки (уже есть) + список `_keyLockedShelfIndices` в определении | Так же сделаны конвейеры: вариант описывает себя сам, валидатор сверяет его с определением |
| Сейф на доске | `ShelfBoard.CloseKeyLockedShelf(shelf)`: заполненная обычная полка, не конвейер и не фильтр | Старый `CloseShelf` с требованием пустоты остаётся для механики с пополнением |
| Момент сбора в игре | `KeyLocksController` слушает новое `GameSession.ShelfResolved(shelf)`. Если впереди колонки ключ, ставит запрос на изменение доски: полка ключа + сейф | Очередь уже даёт резерв, ожидание анимаций, паузу, перезапуск и доигрывание при конце времени. Наследник сессии не нужен |
| Момент сбора в симуляторе | После каждого изменения колонок: собрать ключи впереди → открыть сейфы → разыграть матчи; повторять, пока есть изменения | Одна последовательность для генератора, решателя, валидатора и подсказки |
| Генерация | Обычная генерация с открытыми сейфами, затем расстановка ключей по готовому решению (раздел 5.8). Обратное построение не меняется | Следствие из раздела 2: ключ не меняет ход игры по предметам. Генератор для старых уровней не затрагивается |
| Ранний доступ к ключу | Ограниченный поиск в ширину: нельзя открыть сейф быстрее, чем за `_minimumMovesToFirstKey` ходов | Концепт: глубина ключа ≠ число нужных ходов. Одного длинного решения для проверки мало |
| Порядок сейфов и знаки | Знак — по позиции сейфа в `_keyLockedShelfIndices`: 0 ●, 1 ▲, 2 ■; цвета — латунь, синий, красный | Не хранится в раскладке, нельзя рассинхронизировать |
| Ключ в сцене | `ShelfKey` — `MonoBehaviour` на префабе ключа, рядом с ним `ShelfItemPresentation` (материалы переднего ряда и превью) | Ключ показывается в очереди так же, как предмет |
| Дверца сейфа | Новый `SafeDoorView`, не `ClosedShelfCoverView` | `ClosedShelfCoverView` рассчитан на раскрытие с пополнением и условия. Для сейфа нужны решётка, замок и одно открытие |

**Намеренно используемые шаблоны** (указать в отчётах):
- **Наблюдатель** через события C#: `ShelfResolved`, `KeyLocksController.SafeOpened`.
- **Очередь команд** — существующая очередь изменений доски, новый вид запроса не вводится.

## 5. Архитектура

### 5.1. Модель

**Снимок ключа** (новый, `Assets/Scripts/Model/ColumnKeySnapshot.cs`):
```csharp
public sealed class ColumnKeySnapshot
{
    public int ItemsInFront { get; }
    public int LockedShelfIndex { get; }
}
```
`ItemsInFront >= 0`, `LockedShelfIndex >= 0`; иначе исключение в конструкторе.

**`ColumnStateSnapshot`:**
- новый конструктор `(items, keys)`; старый передаёт пустой список ключей;
- `Keys` — отсортированы по `ItemsInFront`; два ключа на одной позиции запрещены;
- `HasFrontKey` — есть ключ с `ItemsInFront == 0`;
- `FrontItem` возвращает `null`, если `HasFrontKey` (K4);
- `RemoveFrontItem()` — убирает передний предмет и уменьшает `ItemsInFront` у всех ключей; при `HasFrontKey` — исключение;
- `RemoveFrontKey(out ColumnKeySnapshot key)` — убирает ключ впереди;
- `ReplaceFrontItem(ItemType type)` — для обмена, ключи не трогает;
- `MoveFrontToBack` при наличии ключей бросает исключение: ключи с конвейерами не сочетаются.

Все вызовы `new ColumnStateSnapshot(...)` найти поиском по коду и просмотреть: где колонка пересоздаётся из существующей, ключи переносятся явно.

**`ShelfStateSnapshot`:**
- `HasMatch` смотрит на `column.FrontItem`, а не на `Items[0]`;
- `CanMatch` дополнительно требует `IsOpen` (K2). На уровнях с пополнением закрытые полки пустые, их поведение не меняется;
- `WithOpenState(bool isOpen)` — копия полки с другим состоянием;
- `HasKeys`.

**`BoardStateSnapshot`:** `HasKeys`, `KeyCount`.

**Рантайм.**
- `ShelfKey : MonoBehaviour` (`Assets/Scripts/Model/Item/ShelfKey.cs`): `Shelf LockedShelf { get; internal set; }`, `Delete()` по образцу `ShelfItem`.
- `ShelfColumn`:
  - приватный список записей `{ ShelfKey Key; int ItemsInFront }`;
  - `IReadOnlyList<ShelfKey> Keys`, `ShelfKey FrontKey` (ключ без предметов перед ним);
  - `FrontItem` возвращает `null`, если есть `FrontKey`;
  - `AddKey(ShelfKey key, int itemsInFront)`, `ShelfKey TakeFrontKey()`;
  - `TakeFront` уменьшает счётчики ключей; при `FrontKey` — исключение;
  - `PlaceFront` требует пустую колонку **без ключей**;
  - `SwapFrontWith` при `FrontKey` у любой стороны — исключение;
  - `GetQueueSlot(ShelfItem item)` и `GetQueueSlot(ShelfKey key)` — место в очереди с учётом ключей перед ним. Для `ShelfView`.
- `Shelf.CreateSnapshot` переносит ключи. Индекс сейфа знает только доска, поэтому снимок полки с ключами строится через `ShelfBoard.CreateShelfSnapshot`. Перегрузка без доски бросает исключение, если в полке есть ключи.

**`ShelfBoard`:**
```csharp
public bool HasKeyLocks { get; }
public bool IsKeyLocked(Shelf shelf)
public void CloseKeyLockedShelf(Shelf shelf)
public void OpenKeyLockedShelf(Shelf shelf)
```
- `CloseKeyLockedShelf` бросает исключение, если полки нет на доске, она пустая, конвейерная, с фильтром или уже закрыта.
- `OpenKeyLockedShelf` открывает только сейф; повторное открытие — исключение.
- `IsCleared` не меняется. Пустой закрытой полкой может быть только полка с пополнением, а сейф всегда с предметами (проверка валидатора).

### 5.2. Симулятор

`BoardMoveSimulator`:
```
перенос или обмен (колонка с ключом впереди не может быть ни источником, ни целью)
→ ResolveBoard:
     повторять:
        CollectFrontKeys: по полкам и колонкам в порядке индексов снять ключи впереди,
                          открыть их сейфы (WithOpenState(true)), отметить обе полки затронутыми
        ResolveCascades (как сейчас; закрытые полки не матчатся)
     пока на очередном шаге не собран ни один ключ и не было матчей
→ если были матчи и есть конвейеры — сдвиг (на досках с ключами конвейеров нет)
```
- `BoardMoveSimulation`: `OpenedShelfIndexes`, `OpenedShelfCount`. `MatchCount` не меняется.
- `ResolveShelfMatches` (для заблокированных полок в `ShelfBoard.TrySimulateMove`) ключи **не** собирает. Ключ впереди всегда сидит на зарезервированной полке, а с сейфом и самой полкой ход невозможен до конца сбора.
- Публичный `CollectFrontKeys(BoardStateSnapshot board)` — для проверок и генератора.

### 5.3. Отпечаток

- `CreateHash`: у колонки с ключами после предметов дописывается `k<предметов перед ключом>.<индекс сейфа>;` для каждого ключа. Колонка без ключей пишется как сейчас → **хэши уровней 1–20 не меняются**.
- `CreateKey`: колонки внутри полки сортируются, как сейчас; ключи входят в строку колонки. Если `board.HasKeys` или есть закрытая полка с предметами, **полки не сортируются**: ключ ссылается на физический индекс сейфа. Без ключей поведение прежнее.

### 5.4. Данные уровня и валидатор

`TimedLevelKeyLayout` (новый, сериализуемый): `_itemsInFront`, `_lockedShelfIndex`.

`TimedLevelColumnLayout`: `[SerializeField] private List<TimedLevelKeyLayout> _keys`. У старых ассетов список пустой.

`TimedLevelVariant`: ключи передаются в обе стороны (из снимка и в `CreateLayout`).

`TimedLevelDefinition`:
```csharp
[SerializeField] private List<int> _keyLockedShelfIndices = new List<int>();
[SerializeField, Min(1)] private int _minimumKeyDepth = 1;
[SerializeField, Min(0)] private int _minimumMovesToFirstKey;
public IReadOnlyList<int> KeyLockedShelfIndices => _keyLockedShelfIndices;
public bool HasKeyLocks => _keyLockedShelfIndices.Count > 0;
```
`GetMechanicElementCount(LevelMechanic.KeyLocks)` = число сейфов. `LevelMechanic.KeyLocks` добавляется в конец перечисления.

`TimedLevelLayoutRules.MaximumKeyLockedShelfCount = 3`.

`TimedLevelBuilder.Materialize`:
- предметы — как сейчас;
- ключи: `[SerializeField] private ShelfKey _keyPrefab`. Если в раскладке есть ключи, а префаб не задан — исключение с именем сцены;
- сейфы: `CloseKeyLockedShelf` для полок из `_keyLockedShelfIndices`; `CloseShelf` — как сейчас, для полок с пополнением.

**Проверки `TimedLevelValidator`:**

| Где | Проверка |
|---|---|
| `ValidateDefinition` | Индексы сейфов неотрицательны, без повторов, не больше 3. `HasKeyLocks` нельзя сочетать с `HasClosedShelves`, `HasConveyors`, `HasShelfFilters`. `_minimumKeyDepth >= 1`, `_minimumMovesToFirstKey <= _minimumKeyDepth` |
| `ValidateBoard` | Индексы меньше числа полок, вместимость сейфов 3, сейфы не покрывают всю доску. Грубая проверка ёмкости: предметов не больше, чем `(колонки − EmptyColumnCount) × MaximumColumnDepth` |
| `ValidateVariantLayout` | Закрыты ровно сейфы определения (или полки с пополнением — прежняя проверка). Все колонки сейфа непустые. На каждый сейф ровно один ключ. Ключи только на открытых обычных полках. `ItemsInFront` от `_minimumKeyDepth` до числа предметов колонки. Не больше одного ключа на колонку. Глубина колонки вместе с ключом ≤ `MaximumColumnDepth`. В сейфе ключей нет |

Сообщения — в стиле соседних строк валидатора.

### 5.5. Сессия и контроллер ключей

**`GameSession`** — одно изменение:
```csharp
public event Action<Shelf> ShelfResolved;
```
Вызывается в `Update`, когда операция полки снята (ветка `else`: после `_operations.Remove` и `UnlockShelf`). Подписчик может синхронно вызвать `RequestBoardChange`. Запрос сразу резервирует полку: между снятием операции и резервом нет ни одного кадра, когда игрок может взять колонку без переднего предмета.

**`KeyLocksController`** (`Assets/Scripts/KeyLocks/KeyLocksController.cs`) — один объект в SixthLevel.

Зависимости: `LevelSession _session`, `ShelfBoard _shelfBoard`, `List<SafeDoorView> _doors`, `List<KeyLockMark> _marks`, `float _flightDuration = 0.6f`.

```csharp
public bool IsCollecting { get; }
public event Action<Shelf> SafeOpened;
```
- `SessionStarted`: у каждого сейфа доски ровно одна `SafeDoorView`, иначе исключение. Дверцы закрыты со знаками по порядку сейфов, у остальных `SafeDoorView` — `HideForLevel()`. Ключи получают знак своего сейфа.
- `ShelfResolved(shelf)`: для каждой колонки с `FrontKey`, по порядку колонок, — `RequestBoardChange([shelf, key.LockedShelf], completed => PlayCollection(column, completed))`.
- `PlayCollection`:
  1. Модель: `column.TakeFrontKey()`, `_shelfBoard.OpenKeyLockedShelf(safe)`.
  2. Ключ: короткий подскок и перелёт по дуге (`DOLocalPath`) к замку дверцы на масштабированном времени, `SetLink`.
  3. Дверца: `SafeDoorView.PlayOpen(completed)` — замок раскрывается, решётка уезжает вверх.
  4. Колонка ключа: `shelf.View.Advance(...)` — следующий предмет выходит вперёд.
  5. Когда закончились все три анимации — `ShelfKey.Delete()`, `SafeOpened`, `completed()`.
- После `completed` очередь создаёт волну на обеих полках, и возможные матчи разыгрываются обычным порядком (K7). Если впереди оказался следующий ключ, `ShelfResolved` вызовется снова (K8).

### 5.6. Вид

**`ShelfView`:**
- `Refresh`, `Advance`, `RefreshDepth` ставят предмет на место `column.GetQueueSlot(item)`, а не на его индекс. Передний предмет за ключом стоит на месте 1 и показан как превью.
- Ключи ставятся так же: место → поза и масштаб глубины; на месте 0 — `ShowFront`, внутри `_visibleDepth` — превью, иначе `Hide`.
- Без ключей места совпадают с индексами: вид старых сцен не меняется (проверка — скриншоты).
- `PlayConveyorShift` не меняется: ключи с конвейерами не сочетаются.

**`SafeDoorView`** (`Assets/Scripts/View/KeyLocks/SafeDoorView.cs`), на полке-сейфе рядом с `ClosedShelfCoverAnchor`:
- `Shelf Shelf`; `Transform LockPoint` — куда летит ключ;
- `ShowClosed(KeyLockMark mark)`, `PlayOpen(Action completed)`, `ShowOpened()`, `HideForLevel()`, `Cancel()`;
- решётка — меш или примитивы без коллайдеров. Знак на замке — цвет через `MaterialPropertyBlock` и форма (отдельный меш на каждую форму);
- одна анимация на масштабированном времени, `SetLink`.

**`KeyLockMark`** (сериализуемая запись в контроллере): `Color`, `GameObject ShapePrefab` для замка и ключа. Три знака в инспекторе `KeyLocksController`.

**Ключ.** Временная модель — кандидат из концепта (CC0, [Key — low poly](https://opengameart.org/content/key-low-poly)). Перед импортом проверить лицензию на странице, записать источник в `Assets/Models/Keys/SOURCE.md`. Крупное кольцо, толстый стержень, читаемые зубцы. Коллайдеры у ключа не нужны: его нельзя взять.

### 5.7. Подсказка

`MoveSuggestionProvider`: после `simulation.MatchCount` второй критерий — `simulation.OpenedShelfCount` (больше — лучше), потом прежние. Перенос, который освобождает ключ без матча, предлагается раньше бесполезного переноса. Правило K12 «не предлагать ход во время сбора» уже выполняется: на время сбора полки зарезервированы, `HasLockedShelves == true`.

### 5.8. Генератор: расстановка ключей по готовому решению

Новый `TimedLevelKeyPlacer` (`Assets/Editor/TimedLevels/Generation/TimedLevelKeyPlacer.cs`).

Вход: стартовая раскладка с открытыми сейфами, решение генератора, индексы сейфов, `_minimumKeyDepth`, `System.Random` с отдельным сидом (`seed ^ константа`). Так основной `Random` генератора не сдвигается.

```
1. Проиграть решение на открытой раскладке. Для каждого шага записать:
   - сколько предметов ушло из каждой колонки к концу шага (накопительно);
   - какие полки шаг затронул: источник, цель, полки с матчами.
2. Для каждого сейфа L: t(L) = первый шаг, который затрагивает L.
   Если на старте не все колонки L заполнены → отказ LockedShelfNotFilled.
3. Кандидаты на ключ для L: колонка C на открытой обычной полке, не сейф, без другого ключа;
   глубина d от _minimumKeyDepth до числа предметов C на старте;
   шаг появления s(C, d) = первый шаг, на котором из C ушло ≥ d предметов; нужно s ≤ t(L) − 1.
4. Выбор: наибольший s (ключ появляется прямо перед тем, как сейф понадобится),
   при равенстве — наибольшая d, затем случайно. Нет кандидата → отказ KeyPlacementFailed.
5. Закрыть сейфы, вставить ключи и проиграть решение заново:
   каждый ход допустим, матчи те же, каждый сейф открыт до первого обращения к нему, доска пуста в конце.
   Иначе → отказ KeyPlacementFailed.
```

Почему это корректно. Сейф до шага t(L) не трогается ни ходом, ни матчем. Его передние предметы на старте не образуют ряд, иначе генератор не выдал бы такую раскладку. Значит, открытие на шаге s ≤ t(L) − 1 не создаёт новых матчей и не меняет решение. Сам ключ не меняет ход игры по предметам (раздел 2).

`TimedLevelKeyAccessProbe` (рядом). Ограниченный поиск в ширину от стартовой раскладки: можно ли открыть любой сейф быстрее чем за `_minimumMovesToFirstKey` ходов. Состояния — через `BoardStateFingerprint.CreateKey`, бюджет узлов — константа. Исчерпание бюджета — «неизвестно», то есть отказ `KeyAccessUnknown`, а не «прошло».

`TimedLevelVariantGenerator.GenerateCandidates` для определений с ключами:
```
генерация (сейфы открыты) → TimedLevelKeyPlacer → TimedLevelKeyAccessProbe → решатель → кандидат
```
- `CandidateRejection`: `LockedShelfNotFilled`, `KeyPlacementFailed`, `EarlyKeyAccess`, `KeyAccessUnknown`.
- `TimedLevelGenerationInput`: сейфы генерируются **открытыми**, в `ClosedShelfIndices` не передаются.
- Мягкое предпочтение в `CompareReverseMoves` — заполнять сейфы на ранних обратных шагах (то есть поздних прямых). Добавляется, **только если** без него набирается меньше 12 вариантов (этап 3, шаг 4).
- `WriteLayout` пишет ключи.
- Пункт меню `Tools/Timed Levels/Generate Key Lock Levels` по образцу `Generate Conveyor Levels`.

**Готово, когда:** проверки PASS, меню принято пользователем.

### Этап 8. Финальный вид и обучение

1. Ключ: финальная модель, масштаб и ориентация под камеру SixthLevel, короткая подсветка при выходе вперёд. У глубоких ключей постоянного свечения нет.
2. Сейф: решётка и замок в стиле мебели, анимация открытия. При наведении предмета на сейф решётка коротко вздрагивает — по образцу трёхслойного отклика фильтра (`ShelfFilterSignView`), без нового текста.
3. Звук: «щелчок» сбора и «скрип» открытия через SFX-группу микшера, по образцу `MatchAudioPlayer`. Отсутствие клипа не блокирует этап.

5. Стоп-точка: видео сбора и открытия.

**Готово, когда:** пользователь одобрил видео; число вызовов отрисовки SixthLevel выросло не больше чем на 15 относительно заглушек.

### Этап 9. Баланс и приёмка

1. Ручное прохождение 21–25, каждый уровень минимум 3 раза: время, ходы, на каком ходу открылся каждый сейф. Предложить пороги звёзд (стоп-точка: значения утверждает пользователь).

3. Сборка WebGL `TimedCampaignWebGlBuild`: плавность перелёта, отсутствие ошибок в консоли.
4. Финальный прогон всех проверок.
5. Документы: `docs/GDD.md` (правило, глава 5, таблица уровней, генерация с расстановкой ключей), `docs/ГДД_2026-09-30.docx` (раздел изменений), этот план (статус и отклонения).

## 8. Стартовые параметры уровней 21–25 (после этапа 6)

Сейфы — индексы 0, 1, 2 (слева направо). `_emptyColumnCount = 3` везде. Время — старт для тестирования, не итоговый баланс.

| Уровень | Сейфы | Предметов | Типы | `_minimumKeyDepth` | `_minimumMovesToFirstKey` | 3★ / 2★ / лимит | Смысл (дуга концепта) |
|---|---|---:|---:|---:|---:|---|---|
| 21 | 1 | 42 | 6 | 1 | 1 | 1:20 / 1:50 / 2:25 | Правило: ключ близко к превью, польза открытия видна |
| 22 | 1 | 45 | 6 | 3 | 3 | 1:30 / 2:00 / 2:40 | Тот же ключ, путь длиннее |
| 23 | 0, 2 | 48 | 7 | 2 | 2 | 1:40 / 2:15 / 2:55 | Два независимых ключа, выбор очерёдности |
| 24 | 0, 2 | 51 | 7 | 4 | 4 | 1:50 / 2:30 / 3:10 | Ключ через неочевидную подготовку, без угадывания |
| 25 | 0, 1, 2 | 54 | 8 | 3 | 3 | 2:00 / 2:45 / 3:30 | Проверка навыка: три сейфа |

- `_minimumMovesToFirstKey` не больше `_minimumKeyDepth`: при трёх свободных колонках ключ глубины d почти всегда можно открыть за d переносов, и больший порог отбракует почти все кандидаты.
- Если на этапе 6 выбран «короткий поворот», уровни 24–25 повторяют 22–23 с другим числом предметов.
- Типы и число групп по типам — как у соседних глав; порядок групп генератор выбирает сам.

## 9. Риски и открытые вопросы

| Риск | Что делаем |
|---|---|
| Ключ открывается слишком рано, механика не ощущается | `_minimumMovesToFirstKey` и поиск раннего доступа; плейтест этапа 6 |
| Генератор не набирает 12 вариантов: решение трогает сейф слишком рано | Шаг 4 этапа 3, решение об ослаблении — за пользователем |
| Поиск раннего доступа слишком дорог для глубины 4 | Бюджет узлов, «неизвестно» — отказ. Если отказов много — снизить порог уровня, согласовать с пользователем |
| Колонка без переднего предмета (ключ впереди) ломает код, который ждёт `FrontItem != null` у непустой колонки | Найти поиском все обращения к `FrontItem` и `IsEmpty` и просмотреть; полка с ключом впереди всегда зарезервирована. M8, P3, P8 |
| Расхождение игры и симулятора в порядке «сбор ↔ матчи на других полках» | Сбор меняет только полку ключа и сейф, матчи других полок от него не зависят. P1 и P4 сравнивают хэши |
| Решётка закрывает содержимое, игрок не видит пользы | Стоп-точки этапов 4 и 8; при плохой читаемости — увеличить зазор решётки |
| Ключ теряется на фоне ярких предметов | Крупная форма, подсветка при выходе вперёд, знак-форма на ключе |
| Три сейфа забирают 9 из 30 колонок, открытой части тесно | Уровень 25 — 54 предмета на 21 открытой колонке; если генератор или плейтест упираются, снизить число предметов |
| Ручной перенос ключа к замку (вариант B) | Рассмотрен 09.10 и отложен: нужен новый вид хода в модели, решениях, решателе, вводе и подсказке, а тактики почти не добавляет — ключ впереди держать невыгодно. Вернуться, если на плейтесте игроки тянутся взять ключ руками |
| Будущая цепочка ключей (C) нарушает правило «в сейфе нет ключей» | Вне этой работы. Валидатор явно запрещает ключ в сейфе, снятие запрета — отдельный план |
