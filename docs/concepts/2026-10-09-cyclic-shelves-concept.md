# Полки с циклическим счётчиком

Дата: 2026-10-09. Проект: DruggingStuff. Область: конечные уровни кампании.

Статус: концепт для отдельного планирования. Выбранное пользователем направление и единица уменьшения счётчика зафиксированы; остальные предложения требуют подтверждения перед реализацией.

## 1. Суть и ценность для игрока

Некоторые заполненные полки периодически меняют доступность. Игрок видит, через сколько результативных ходов открытая полка закроется, а закрытая откроется.

Новое решение: какие предметы нужно перенести и какие группы подготовить до следующего переключения. Матч продвигает очистку и одновременно меняет будущую доступность пространства.

Пример: особенная полка закроется через один результативный ход. Игрок сначала выносит с неё нужный предмет обычным переносом без матча, затем собирает готовую группу на другой полке. Альтернативно он может закончить матч на самой закрывающейся полке до потери доступа.

Гипотеза: предсказуемые окна доступности заставляют осознанно готовить раскладку, не требуя нового способа перетаскивания или отдельного таймера.

## 2. Принятые решения и предложения

| Статус | Решение |
|---|---|
| Задано пользователем | На уровне несколько особенных полок, среди них могут быть открытые и закрытые. |
| Задано пользователем | При обнулении счётчика закрытая полка открывается, открытая закрывается. |
| Подтверждено пользователем | Счётчик уменьшается один раз за ход с хотя бы одним матчем. Двойной матч и каскады дают одно уменьшение. |
| Задано пользователем | Если предметы остались только за закрытием, требуется автоматическое открытие для продолжения. |
| Предложение | После переключения счётчик восстанавливается до периода своей полки, цикл повторяется. |
| Предложение | Первые две полки имеют одинаковый период и противоположные состояния. |
| Предложение | Часть обычных полок всегда открыта; пополнения нет. |
| Требует подтверждения | Расширенное обнаружение тупиков и постоянное открытие всех особенных полок при аварийном переходе к доигрыванию. |

Базовая модель: конечное содержимое, повторяющийся цикл, один счётчик на особенную полку. Для первого прототипа значения синхронизированы; разные периоды — последующее развитие.

## 3. Правила предлагаемой первой версии

1. Особенная полка имеет начальное состояние, положительный период и оставшееся число результативных ходов до переключения.
2. Предметы существуют с начала попытки. Закрытие не уничтожает их, не меняет порядок и не создаёт пополнение.
3. На закрытой полке запрещены взятие, перенос, обмен и матчи.
4. Обычный ход без матча ничего не меняет в счётчиках.
5. Один принятый ход с любым количеством матчей уменьшает все активные счётчики на один.
6. При достижении нуля состояние соответствующей полки инвертируется, затем счётчик восстанавливается до её периода.
7. Изменения полок, обнулившихся одновременно, образуют одну согласованную смену состояния. Игрок не получает промежуточный момент для переноса между её частями.
8. Матчи после открытия разрешаются как автоматическое последствие. Они не уменьшают счётчики повторно.
9. Пустая закрытая полка не должна мешать победе, если на всей доске больше нет предметов и незавершённых последствий хода.
10. Пауза останавливает анимации. Принятые до тайм-аута действия доигрываются по текущему правилу кампании.

Рекомендуемый стартовый период — три результативных хода. Это параметр проверки, а не готовое значение баланса.

## 4. Порядок обработки и параллельные действия

1. Закончить исходный перенос/обмен и все его матчи.
2. Зарегистрировать ровно один результативный ход.
3. В детерминированном порядке вычислить новые счётчики и список переключений.
4. Зарезервировать затронутые полки, дождаться уже принятых операций на них и завершить смену состояния.
5. Разрешить возникшие на открытых полках матчи без нового шага цикла.
6. До проверки результата выполнить проверку аварийного открытия, если доска стабилизирована.

Использовать существующую очередь изменений доски. Полки не должны закрываться под уже принятым переносом. Остальные свободные полки сохраняют возможность взаимодействия, как сейчас при конвейерах.

Два отдельных принятых результативных хода дают два уменьшения, даже если их анимации пересеклись. Не объединять их в один шаг и не связывать число шагов с частотой кадров. Порядок обработки завершившихся операций должен быть определён одинаково для модели и реального исполнения; для сертификатов прохождения ходы воспроизводятся последовательно.

Перед техническим планом проверить: достаточно ли текущей очереди для корректного резервирования нескольких пересекающихся запросов. Не считать наличие RequestBoardChange доказательством, что все новые сочетания уже обработаны.

## 5. Тупики и аварийное открытие

### Подтверждённый случай

Все доступные полки пусты, но за закрытием есть предметы. Продвинуть счётчик невозможно; нужно открыть доступ к содержимому автоматически.

### Дополнительный случай

На открытых полках есть два мяча и один медведь, за закрытием — один мяч и два медведя. Переносы возможны, однако ни один матч на открытой части невозможен. Проверка одной пустоты не спасает такую ситуацию.

Отсутствие готового матча и отсутствие хода, который даёт матч сразу, не доказывают тупик: матч иногда требует нескольких подготовительных переносов. Текущая подсказка не является доказательным детектором разрешимости.

### Предлагаемая защита для прототипа

На стабилизированной доске проверять:

- Ноль предметов на открытых полках при ненулевом общем количестве — обязательное открытие.
- Для обычных трёхместных полок ни один тип среди всего открытого содержимого не встречается хотя бы три раза — ещё одно достаточное доказательство невозможности получить матч без открытия.

Вторая проверка рассматривает всю глубину открытых очередей, а не только передние предметы. Наличие трёх предметов одного типа не доказывает, что их можно собрать: это лишь исключает один простой вид тупика.

Предложение: при обнаружении такого состояния открыть все особенные полки и отключить цикл до конца попытки. Показать краткое понятное объяснение перехода к доигрыванию. При этом текущие запросы именно этого цикла должны перестать повторно закрывать полки.

Это защита от описанных случаев, не гарантия прохождения любой раскладки. Перед публикацией нужны проверка решений, исследование достижимых состояний и отдельное решение о более сложных блокировках. Если используется ограниченный поиск, исчерпание его бюджета означает «неизвестно», а не «тупик».

Если аварийное открытие часто требуется в середине уровня или игрок намеренно вызывает его ради упрощения, пересмотреть раскладки/правило. Предложение про постоянное открытие не утверждено пользователем: альтернатива — открыть дополнительные полки с сохранением цикла, но тогда отдельно решается риск повторной блокировки.

Проверку выполнять до HandleBoardSettled/объявления результата, например через существующую фазу SettleBoard. Событие BoardSettled в текущем GameSession приходит уже после обработки результата и не подходит для единственной обязательной защиты.

## 6. Представление

Постоянная дверца или шторка с обратимой анимацией. Пыль, исчезающая навсегда, плохо объясняет повторный цикл.

На каждой особенной полке:

- Число оставшихся результативных ходов.
- Значок следующего состояния: откроется или закроется.
- При значении 1 — заметное, но короткое предупреждение.
- Видимое через решётку содержимое для подготовки следующих действий.

При синхронном цикле нескольких полок показывать их общую связь. Сигнал переключения не должен выглядеть как новый отдельный таймер реального времени.

Первая обучающая формулировка: «Каждый ход с совпадением приближает смену полок». Точный текст проверить с игроками и локализовать вместе с данными главы.

### Предлагаемое разделение ответственности

Доска хранит доступность и содержимое. Небольшая модель цикла хранит период, остаток, состояние и признак перехода к доигрыванию. Контроллер реагирует на завершение результативного хода, отправляет изменение доски и обновляет представление.

Правило уменьшения и переключения должно быть одним для исполнения и симуляции, без зависимости от анимаций. Отдельная универсальная система состояний всех будущих механик не требуется.

Снимок/отпечаток состояния включает остатки счётчиков, периоды, начатый режим доигрывания и физическую принадлежность счётчиков полкам. Одинаковые предметы с разными остатками — разные состояния. Не переставлять особенные полки при нормализации без доказанной эквивалентности.

Подсказка должна оценивать последствия следующего переключения. Перенос без матча, который спасает нужный предмет от закрытия, может быть полезнее немедленного матча.

## 8. Раскладки и сочетания

Первый прототип: две особенные полки с противоположными состояниями и одинаковым периодом; несколько постоянно доступных обычных полок; ограниченное, но достаточное число свободных колонок. Решение проверяется вручную и воспроизводится симуляцией.

Наличие всегда открытой полки или свободного буфера само по себе не гарантирует доступность следующего матча. Слишком много свободного места тоже опасно: игрок может вынести всё содержимое до первого переключения и почти не замечать цикл.

После подтверждения гипотезы можно проверить пять шагов освоения: один видимый переход; повторяющийся цикл; подготовка перед закрытием; более насыщенные очереди; финал с освоенными параметрами. Разные периоды добавлять только после проверки читаемости общего цикла.

Фильтры и конвейеры пока не включать в базовую версию. Текущий код запрещает эти сочетания с закрытыми полками. Для будущего сочетания отдельно определить: двигается ли закрытая лента, как взаимодействуют два последствия одного хода, что происходит с привязанным типом при закрытии его единственной коробки.

## 9. Прототип и решение о развитии

Вопрос: использует ли игрок подготовительные ходы, чтобы управлять моментом смены доступности?

Нужны две фиксированные раскладки: простая для понимания и вторая с выбором между немедленным матчем и полезной подготовкой. Добавить отдельные технические случаи аварийного открытия.

Наблюдать: предсказывает ли игрок следующее состояние; выносит ли предметы заранее; оставляет ли подготовленные группы к открытию; сколько раз требуется спасение; возникают ли бесполезные матчи ради ожидания.

Развивать, если цикл даёт предсказуемый выбор и игрок способен объяснить собственный план. Пересмотреть, если смена воспринимается случайной, ожидание доминирует или защита от тупика фактически решает уровень вместо игрока.

## 10. Этапы реализации и приёмка

1. Подтвердить восстановление счётчика, начальные фазы и политику аварийного открытия.
2. Поддержать заполненные закрытые полки, запрет скрытых матчей и цель завершения нового режима.
3. Добавить чистую модель цикла, её состояние в снимках и симуляции.
4. Подключить MatchingMoveResolved, очередь изменений и защиту до проверки результата.
5. Добавить обратимую дверцу, счётчики и два уровня прототипа; проверить игровой смысл.
6. При положительном результате — генерация и проверка вариантов, подсказка, обучение, глава и баланс времени.
7. Отдельно проверить Play Mode и браузерную сборку.

Обязательные сценарии: перенос без матча; обычный матч; двойной матч обменом; длинный каскад; автоматический матч после открытия; несколько отдельных результативных ходов с пересекающимися анимациями; закрытие занятой полки с сохранением очередей; ноль открытых предметов; открытые предметы без достаточных количеств для матча; пустая закрытая полка в конце; пауза/перезапуск; тайм-аут до завершения переключения; отсутствие повторного закрытия после аварийного открытия; совпадение исполнения с симуляцией; регрессия прежних refill-уровней.

Предварительная сложность: высокая. Главные затраты — корректность динамической доступности, обратимые эффекты, защита от блокировок и проверка раскладок. Сами счётчики относительно просты. Полный срок оценивать после выбора политики спасения.

## 11. Решения перед техническим планом

- Подтвердить повторный сброс до периода после каждого переключения.
- Общий период первых полок и их начальные остатки.
- Какая информация о содержимом остаётся видимой.
- Открывать при блокировке все полки навсегда или сохранять цикл по другому правилу.
- Какие тупики обязана обрабатывать игра и что должно предотвращаться контентом.

Рекомендуемый старт: две противоположные полки с периодом 3, постоянные обычные полки, конечный набор, одна явно объяснённая защита с переходом к доигрыванию.
